# Operations

How the site and the API are deployed and configured, how the offline cache behaves and how to turn it off, and what CI runs.

## Deploys

- **Web (GitHub Pages).** CI deploys `main` once `ci-ok` passes on it: the `pages-build` job in `.github/workflows/ci.yml` builds the commit CI is testing (`.github/workflows/build-pages.yml`) while the tests run, and once `ci-ok` passes the `deploy-pages` job deploys that build (`.github/workflows/deploy-pages.yml`). Running the **Deploy web to GitHub Pages** workflow by hand (Actions → Run workflow, on `main`) deploys `main` at once, without waiting for CI. Only `main`'s newest commit is deployed: an older run skips, and one Pages deploy runs at a time.
- **API (Cloudflare Worker + D1).** The `deploy-api` job in `ci.yml` calls `.github/workflows/deploy-api.yml` the same way, when the `DEPLOY_API` variable is `true`, with `secrets: inherit` so the `cloudflare` environment's secrets resolve in the called workflow. It uploads only a build the live Worker is not already running: it fingerprints the build, skips the migrations and the upload only when `GET /v1/version` on `PRICES_API` already reports that fingerprint, and otherwise deploys and then fails unless the live API reports the new build within about a minute (with `PRICES_API` unset it always deploys and only warns that it could not check). First deploy, updates, migrations and turning on deploys from GitHub: [api/README.md](../api/README.md#deploys-from-github). **Set up on 2026-11-26:** the repository variable `DEPLOY_API` is `true` and the `cloudflare` environment (`main` only) holds `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, so CI checks the live Worker after every green run on `main` and deploys it when its build differs; don't ask the owner to set it up or to create a token again. The same "sol-y-cerveza deploy" token (expires 2027-11-24) is also a network secret for `api.cloudflare.com` on the owner's Claude cloud environment `sol-y-cerveza`, so a cloud session there can deploy by hand if CI's deploy fails: from a clean checkout of `main`, `cd api && npm ci`, then `CLOUDFLARE_API_TOKEN=<any placeholder> npx wrangler d1 migrations apply sol-y-cerveza --remote` and `npx wrangler deploy` (the session's proxy puts the real token in). A deploy without `--var BUILD_ID:<fingerprint>` makes the live API report `build: null`, so the next CI run on `main` deploys again and stamps it; [api/README.md](../api/README.md#deploys-from-github) has the commands that stamp it by hand.
- **`trees.json`, `buildings.json` and `bridge-mesh.json`** live on the `height-tiles` branch, not on `main`: every Pages deploy copies them into `data/` ([pipeline](pipeline.md#map-shadows)). The deploy fails if that branch is missing; without `bridge-mesh.json` the map draws no Puente Real pylon or cables and keeps the basemap's bridge roads.
- **Data.** The admin's Publish pushes a `data/venue-review-*` branch; the **Publish review** and **Publish review PR** workflows check it, open its PR and enable auto-merge ([admin guide](admin.md#publish)). Once merged, the deploy above ships it.
- **Mobile** is paused: `.github/workflows/mobile.yml` only runs by hand ([mobile](mobile.md)).

**Usage counters.** The app's anonymous daily counters (ADR-0013) live in the `event_counts` table; read them with `GET /v1/admin/stats?days=N` and the admin token, or with `wrangler d1 execute`: [api/README.md](../api/README.md#usage-counters). Their migration ships like any other (CI applies it before deploying the Worker).

**Worker logs.** The Worker keeps no per-request invocation logs, on purpose (`[observability.logs] invocation_logs = false` in `api/wrangler.toml`, issue #495). Workers Logs (Cloudflare dashboard → the Worker → Logs) still show entries for errors: `console.error` (misconfiguration such as `IP_SALT` or a Turnstile test secret, server errors) and uncaught exceptions, which may carry Cloudflare's own request metadata (not inspected). README.md's Privacy section relies on this, so to debug a request, reproduce it locally (`npm run dev` in `api/`) or watch it live with `wrangler tail` rather than turning invocation logs back on.

## Offline and the service worker

Why network-first: [ADR-0011](adr/0011-network-first-service-worker.md). The built site registers `sw.js` (source `web/sw/sw.ts`, emitted by the `serviceWorker` plugin in `web/vite.config.ts`) once the page has loaded and the map has drawn its first view (or 15 s after the load event if it never does), so on a first visit the install's downloads (the LiDAR files, about 0.5 MB) don't compete with the basemap's first tiles. It is never registered in dev (`npm run dev`, `npm run admin`), in the admin or inside the Capacitor apps (`web/src/registerServiceWorker.ts`).

| Request                                                                                                               | Strategy                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `assets/*-<hash>.*`                                                                                                   | Precached at install, cache-first; chunks only owner tools import (exifr, for photos) are cached on first use. One cache per build (`syc-app-<build>`); the previous build's is kept so pages still open on it keep working.                                                                                                                                                     |
| The page, `data/terraces.json`, `data/buildings.json`, `data/trees.json`, `data/bridge-mesh.json`, icons, other files | Network-first, past the HTTP cache (revalidated), 3 s timeout; the cache only when offline, slow or on a 5xx. A late response still updates it. The page and the four data files are also fetched at install, so the app opens offline from the second visit, with its shadows and the bridge. Without the two LiDAR files the map shows the basemap's buildings and no shadows. |
| OpenFreeMap style and TileJSON                                                                                        | Network-first with the same timeout (they name the tile version to load).                                                                                                                                                                                                                                                                                                        |
| OpenFreeMap tiles, glyphs, sprites                                                                                    | Stale-while-revalidate, at most 600 entries and 30 days; CORS responses only, never opaque ones.                                                                                                                                                                                                                                                                                 |
| Prices API `GET /v1/prices`                                                                                           | Network-first; also fetched at install. Writes (`POST /v1/changes`, `POST /v1/reports`, owner mode's `/v1/owner/*`) and everything else are not touched.                                                                                                                                                                                                                         |

**Updates.** A new worker takes over at once (`skipWaiting`, `clients.claim`) but never reloads an open page; its next load is the new version. If a page asks for a map chunk that a deploy removed and no cache has, `LazyMapView` reloads once (guarded by `sessionStorage`, no loops) and then shows "No se pudo cargar el mapa".

**Kill switch.** If the worker misbehaves, set the repository variable `SW_KILL_SWITCH` to `1` (Settings → Secrets and variables → Actions → Variables) and run the **Deploy web to GitHub Pages** workflow on `main` (Actions → Run workflow). A manual run deploys `main` at once, without waiting for CI; a merge to `main` also redeploys, but only once CI passes on it (the `deploy-pages` job in `ci.yml`, after `ci-ok`). That build ships `web/sw/kill-switch.ts` as `sw.js`: browsers check `sw.js` on every visit, even when the app's own code is broken, and it deletes the site's caches and unregisters itself; the page also unregisters and clears them. Pages are not reloaded under the user. Delete the variable (or set it to `0`) and deploy again to turn caching back on. Without CI: `cd web && VITE_SW_KILL_SWITCH=1 npm run build` and publish `dist/`.

## CI

`.github/workflows/ci.yml` runs on every PR and every push to `main`:

| Job                          | Runs                                                                                                                                                                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `changes`                    | decides which jobs the PR can affect (below)                                                                                                                                                                                                         |
| `web`                        | `npm ci`, `format:check`, `lint`, `test`, `build` in `web/`                                                                                                                                                                                          |
| `e2e`                        | Playwright, four jobs: `phone`, `desktop`, `reports` (`reports-phone,reports-desktop`) and `offline`, each with `E2E_PROJECTS` set to its projects. Chromium's system libraries are installed only if one is missing (the runner image has them all) |
| `pipeline`                   | `uv sync --locked`, `ruff format --check`, `ruff check`, `mypy`, `pytest` in `pipeline/`                                                                                                                                                             |
| `api`                        | `npm ci`, `format:check`, `lint`, `typecheck`, `test`, `build:dry`, and every D1 migration applied to a fresh local database                                                                                                                         |
| `ci-ok`                      | the single required check: fails if any job failed or was cancelled, or (outside a PR) was skipped                                                                                                                                                   |
| `deploy-pages`, `deploy-api` | pushes to `main` only, after `ci-ok`; `deploy-pages` ships the build `pages-build` made while the tests ran; `deploy-api` skips the upload when the live Worker already runs the build                                                               |

**Path filter.** On a PR, `.github/scripts/ci-changes.sh` maps the changed paths to the jobs that read them, and the others are skipped (a skipped job counts as passed for `ci-ok`). Changes under `.github/` run everything; `web/ios/**`, `web/android/**`, `docs/`, `README.md`, `CLAUDE.md` and other files outside the code run nothing but `changes` and `ci-ok`. The full mapping is in the script and repeated above the `changes` job. Pushes to `main` run everything.

**e2e projects** (`web/playwright.config.ts`): `phone` and `desktop` on the dev server, `reports-phone` and `reports-desktop` on a dev server with a stubbed prices API and Turnstile key, and `offline` against production builds served under `/sol-y-cerveza/` by `web/scripts/sw-test-server.mjs`, which builds them first and can switch between two deploys and the kill switch. Locally, `cd web && npm run e2e` runs all five (install the browser once with `npx playwright install --with-deps chromium`); `E2E_PROJECTS=phone,reports-phone npm run e2e` runs only those.

**Other checks.** `pr-title` (`.github/workflows/pr-title.yml`) checks the PR title is a Conventional Commit, since it becomes the squash commit. CodeQL code scanning (set up in the repository settings; there is no workflow file) scans the workflows, JavaScript/TypeScript and Python; a new alert of high severity or above blocks the merge. Dependabot (`.github/dependabot.yml`) opens weekly updates for `web/`, `api/`, `pipeline/` and the GitHub Actions.

**Mobile** (`.github/workflows/mobile.yml`) is manual only and not a required check ([mobile](mobile.md#what-ci-builds)).

## Brand images

The app icons in the web manifest (`web/public/icon-*.png`) and the link preview image (`web/public/og.png`) come from `web/public/favicon.svg`: regenerate them with `cd web && npm run brand-images` (needs Playwright's Chromium, and uv for the lossless oxipng recompression it ends with). See the [design standards](design/README.md).
